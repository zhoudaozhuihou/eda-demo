数据部门 ETL 组可落地的 Data Agent 方案

范围收窄版：只做 ETL 组拥有数据管道、指标口径与元数据控制权的部分
2026-11-17 适用：Global Bank 数据部门 ETL 组 交付：能力清单 + 架构 + 数据源方案 + 最小化 MVP + 12 个月路线 + 验收指标 + 银行落地案例
结论：ETL 组不需要"买一个 Data Agent"。正确做法是把 Agent 嵌进已有的数据链路，交付一个可信数据服务层：语义指标层 + 目录血缘 + 质量规则 + 只读数据服务（API/MCP）+ 轻量编排。Agent 只做读取、解释、生成草稿、提出建议；所有写入生产管道、指标定义、权限变更的动作都停在 PR 和人工审批。

1. 职责边界：做什么，不做什么

ETL 组可直接负责需要协作或上移，不在本方案
  • 多源数据接入：CDC、批量、文件、API、流式落地
  • 清洗、标准化、编码映射、主数据对齐、去重
  • ETL/ELT 开发与调度：SQL、dbt、Spark、Airflow 等
  • 指标与语义层：定义、版本、Golden queries、口径解释
  • 数据质量：规则、新鲜度、漂移、告警与根因定位
  • 元数据、目录、血缘、影响分析、PII 标记建议
  • 数据服务化：只读视图、API、受管 MCP server
  • 数据资产评测：golden set、回归、答案引用与审计日志
  • 内部数据助手：问数、取数、口径、质量、编目、代码草稿
  • 核心银行/总账系统的写入与业务操作
  • 信贷、风控、反洗钱、客户准入等决策
  • 监管报送的最终签署与对外解释
  • 全行权限体系、模型风险管理、合规审批
  • 客户侧产品、面向客户的 AI 助手
  • 跨境数据传输合规判定、模型训练平台与 GPU 基建
  • 业务指标"是什么"的最终裁定（业务 owner 决定，ETL 组实现与维护）
边界原因：ETL 组拥有的是"数据怎么来、怎么算、怎么被找到"，没有业务决策权、风险审批权和监管解释权。因此本版删除了全行级 Agent 控制面、业务自治级别、模型风险治理、监管签署等内容——不是它们不重要，而是它们不属于 ETL 组的交付范围。

2. 技术路线：先做数据服务层，再做 Agent

第一优先
语义指标层

dbt MetricFlow / Cube / Wren MDL，Git 版本化，PR 审阅。银行场景纯 NL2SQL 准确率仅 40–60%，加语义层后可达 92–95%。

第二优先
目录与血缘

DataHub 或 OpenMetadata。让 Agent 先找到"被认证的数据"，再谈查询；同时支撑影响分析与口径溯源。

第三优先
质量与评测

质量规则 + 30–100 条真实问题 golden set + 回归门禁。评测不过不上线，这是 ETL 组能自证的价值。

第四优先
只读服务化

数仓原生 MCP（UC / Snowflake / Fabric）或自建只读 API，按域拆分、白名单、限流、全链路日志。

平台层面不强制选型：行里已有 Databricks 就用 Unity Catalog + Genie，已有 Snowflake 就用 Cortex/Semantic Views，已有 Fabric 就用 Fabric Data Agent。但语义定义、golden queries、质量规则和评测集必须放在 ETL 组可版本化、可迁移的资产里，不能只存在于某个厂商产品中。

3. ETL 组视角架构

控制点：Agent 不直接修改生产管道、指标定义或权限。接入助手和代码助手只产出草稿，走 Git PR + 人工 review；问数与口径助手只读；所有调用记录用户、查询、引用和结果；评测集不通过则阻断上线。

6. 最小化 MVP：8 周跑通一个可信闭环

MVP 定义：6–8 周内，在一个数据域上让一个只读问数 Agent跑通"提问 → 口径解析 → 生成 SQL → 返回带引用的结果 → 审计留痕"的完整闭环，用 Golden set 证明准确率 ≥90%，并用 ETL 组取数工时的实际下降证明价值。MVP 的目标不是"能答很多"，而是"答的每一个数都可信"。

六个"一"——把范围压到最小

维度MVP 只做刻意不做
场景内部智能问数（ETL 组 + 1–2 个种子业务方），只回答"数是多少 / 口径是什么"全行问答、主动洞察、预测
数据域1 个质量最好、问得最多的域（存款 / 客户 / 交易 选其一）第二个域、跨源 JOIN、联邦查询
指标10–20 个高频指标，业务 owner 签字冻结口径全量指标、动态口径
技术栈复用行内已有平台 + 自有 Git 语义资产，零新增采购新买产品、新建控制面
链路NL → DSL/MQL → SQL → 只读查询 → 带引用回答；身份穿透 + 审计写生产管道、改指标定义（只出 PR 草稿）
度量Golden set 准确率、引用完整率、越权零通过、取数工时下降业务 ROI、厂商 Demo 准确率

7. DeepSeek Harness / Super-agent 如何融入

先定性：这两者都不是 Data Agent 产品，而是 Agent 的运行时框架（Harness）和架在其上的主动式多任务架构（Super-agent）。它们落在架构图的"ETL 内部 Agent（轻编排）"与"审计/评测"位置，不替换语义层、不替换数据服务层、不碰生产管道。价值是补齐我们原来最薄的一环：可插拔的运行时 + 天然的全链路轨迹；风险是它们的权限模型完全达不到银行生产要求，必须按第 7.3 节红线改造。

7.1 它们分别是什么

项目本质关键事实（官方/一手）
DeepSeek Harness（dsh）开源 Agent 运行时框架，Model + Harness = Agent2026 年 8 月以 MIT 开源，基于 Cordis 的"everything is a plugin"：模型、工具、技能、会话、沙箱、存储、循环、调度、UI 全是插件，配置即可换。模型无关（OpenAI/Anthropic/Google/Kimi 等 40+ 提供方）。四种模式：Standard / Code / Minimal（两工具极简，用于模型 benchmark）/ Creator。全链路 append-only session log：系统提示、推理、工具调用与结果、Subagent 调度、每次上下文注入都记录，可 resume / fork / search / replay。11-17 已支持"按 agent 按需加载 MCP 工具"。仍处 developer preview，官方预告"必有破坏性变更"。
Super-agent（dsh-superagent）装在 Harness 上的主动式架构原型，源自 coding agent 场景10-31 发布的架构探索 + 开源原型（MIT）。Router 常驻接收 GitHub / 飞书 / 邮件消息并分派；Worker 独立上下文、按工单并行、可再调 Subagent；Watchdog 盯死循环。事件驱动 + 两级过滤（规则先筛、模型再判）；投机执行=后台静默复现、确认才提交否则沉默；存算分离（执行云端、状态入库、本地轻量 daemon）。授权用 Policy/Mandate：白名单、explicit/inferred/not-admitted 三级、accept mode off/observe/auto、策略版本与恢复前重校验。原型仅一次 commit，README 自述"研究代码、非官方产品、可能与内部版本不同、部分设计未实现"。

7.2 能力映射：接到我们设计的哪一层

Router/Worker + 事件驱动 + 投机执行质量巡检 / 主动洞察草稿把质量规则失败、血缘变更、CI 结果做成 trigger；"静默复现并修复"= 后台先复现、确认后才提草稿 PR，正好符合"草稿走 PR + 人工审批"它源自"issue → PR"的编码场景，触发器要改造成数据域事件；只出草稿，不自动合并
授权 Policy / observe→auto / 策略版本渐进式自治 L0–L3先在 observe 模式跑一段看 Decision 记录，再决定是否 auto；策略版本变更可重校验在途工单——这是很好的"自治级别可审计"证据accept mode 默认 observe；任何 auto 都要先在隔离环境验证，且保留人工停止开关
Watchdog / 后台任务 30 分钟上限熔断 / 资源治理防死循环、防跑飞，对应我们的 kill switch、限流与超时预算超时只 kill shell job，Subagent 可继续；要自己做端到端超时与成本上限

7.3 红线：官方明确写的、必须写进设计的限制

  • 官方 safety notice 原文：experimental、未经安全审计、不得视为安全或生产就绪；可执行模型生成的代码、加载第三方插件、访问网络/进程/凭证/文件。→ 不作生产控制面；只做 ETL 内部工具或隔离环境 PoC，锁定版本。
  • Worker 以操作者 OS 账户执行命令且无逐条审批；原型文档自述包装脚本"不是安全边界"，可用绝对路径绕过。→ 绝不给生产写权限；专用低权账号 + 容器/VM + 只读库凭证；写动作只在隔离 Git 副本，PR 由人合并。
  • 沙箱、审批提示、权限控制不保证隔离，官方要求"不要作为不受信任工作负载的唯一安全控制"。→ 纵深防御；权限在语义层/网关独立强制，沿用原设计，不因用了 Harness 而削弱。
  • 插件生态庞大但质量参差（社区数月产出数千插件）。→ 内部插件仓库 + 白名单 + 代码审查；禁止运行时自动安装未审插件。
  • Super-agent 是单 commit 研究原型，与内部版本不一致、部分设计未实现、可能有 bug。→ 只读其架构思想，不当产品上线；Router/投机执行/授权策略可借鉴，实现要自研或加固。
  • developer preview 预告破坏性变更。→ 锁 commit、离线评估升级、CI 回归；不把核心链路绑在 unpinned 版本上。

7.4 在 MVP 里的用法（分阶段）

MVP W4–5 可用

用 dsh 作内部 Agent 的运行时骨架（替代自研轻编排），把只读数据源与语义层做成 MCP/插件；用它的 session log 出审计轨迹。保持运行时可替换——模型无关与插件化正是为了不被绑定。

P1 之后 PoC

借鉴 Super-agent 的"事件触发 + 静默复现 + 只提草稿"做质量巡检 Agent，放在隔离环境，人工合并 PR；先 observe 再谈 auto。

明确不上线

客户面问答、任何写生产管道的动作、任何监管报表链路。这些仍走行内既有审批与治理体系。

一句话结论：Harness 值得作为 ETL 内部 Agent 的运行时候选——它的插件化和全链路轨迹正好命中 MVP 的审计与可插拔需求；Super-agent 值得抄架构思想——主动式巡检与渐进授权。但两者当前都不具备直接进银行生产的资格。用它们的工程红利，不用它们的权限模型；权限判定始终留在我们自己的语义层与网关。

8. Data Agent 辅助数据开发全生命周期：开发 · 测试 · 验证 · 发布

定位：API 辅助构建只是 Data Agent 的一个应用。真正要做的是让 Data Agent 贯穿数据开发的全生命周期——需求、开发、测试、验证、发布、运维，覆盖 API / 文件 / 代码 / 数据资产 各类产物。全程是副驾驶（copilot）而非自动驾驶：Agent 出草稿、跑检查、备产物；人做设计决策、测试签字、发布批准。任何产物从草稿到生效，都必须经过人工审核，Agent 自己不能让任何东西上线。

8.3 六道审核门禁：贯穿所有阶段与产物

需求 → 语义模型定位 → Agent 出草稿 → 设计评审 → 开发 PR → 测试齐套 → 验证回归 → 多方签字 → 发布（API/文件/代码）→ 运行时只读+限流+审计

门禁 1 · 口径锚定

任何阶段先定位到认证指标；找不到就拒绝生成，绝不"临时拼一个"。

门禁 2 · 设计评审

结构、命名、兼容性由数据 + 应用 owner 评审，未签字不进开发。

门禁 3 · 测试齐套

单元/质量/契约/越权测试全绿，覆盖率由 QA/安全签字，不过不可合并。

门禁 4 · 验证回归

Golden set 与口径一致性通过、血缘影响已评估、越权 0 通过，否则阻断发布。

门禁 5 · 发布审批

变更单 + 多方签字齐全才可发布；Agent 不持有发布凭据、网关注册权与文件外发权。

门禁 6 · 全程留痕

生成轨迹与审核记录一并归档，可回答"这个产物怎么来的、谁审的、依据是什么"。

最危险的失效模式：把"辅助"做成"绕过"。 如果 Agent 生成的代码直连物理表、文件绕过受控通道外发、或跳过验证直接发布，就等于在治理体系外开了新入口。硬性要求：代码经语义层取数、文件走受控通道、验证全绿、签字齐全才可发布。

8.5 Harness / Super-agent 作为全生命周期运行时

  • Harness 作统一构建运行时：Creator mode 定制不同阶段的预设（builder / tester / validator / packager）；append-only 轨迹记录每次生成与检查的提示、上下文与产物，让审核人看到"这个草稿是怎么来的"。
  • Super-agent 借鉴"静默草稿 + 事件触发"：草稿本地验证通过才提 PR/变更单，失败不打扰人；测试失败、质量告警、CI 结果可作为触发。授权保持 observe + 人工 accept，不启用 auto 模式——审核权始终在人。
  • 权限边界不变：Harness Worker 以操作者账户无审批执行，因此全生命周期 Agent 只运行在隔离环境、低权账号、只写 Git 工作副本；发布凭据、网关注册权与文件外发权不交给 Agent。
一句话：Agent 覆盖开发到发布每一步的草稿与检查，把重复劳动做到 80 分并附上证据；人负责设计与发布的最后 20 分判断与签字。审核不是补一道手续，而是贯穿全生命周期的主干——任何产物能否生效，只取决于人是否批准。

12. 银行落地案例与收益证据（截至 2026-11）

先看结论：真正落到生产的银行 Data Agent，几乎都不是"大模型直连数据库裸问"，而是语义层 / 指标平台 + 多智能体分工 + 人工审核——和我们前面收敛的路线一致。公开的收益高度集中在三个可量化维度：时效（小时/天级 → 秒/分钟级）、质量（准确率或采纳率 92%–100%）、人力（工时、人年、重复取数工作量显著下降）。纯 NL2SQL 在银行复杂口径下没有找到生产级收益证据。

13. 语义层怎么在银行落地：实现蓝图

一句话定位：语义层不是"给表加中文注释"，而是把口径、关系、权限、时间属性从大模型提示词和散落的 SQL 里抽出来，变成一份可版本化、可编译、可审计的契约。ETL 组真正要交付的是这份契约 + 把它编译成查询的引擎；大模型只负责把用户问题映射到这里面已经定义好的东西。

13.1 语义层要实现的东西：四层契约

层定义什么银行里为什么必须有落地产物
① 逻辑模型层业务可见的表 / 视图、列、显式 JOIN 关系；未暴露的列对查询方物理不可见核心、信贷、理财系统表结构混乱且文档残缺；不收口就等着 Agent 猜字段、猜 joinmodels / relationships 定义文件，写入 Git
② 指标定义层原子指标（贷款余额、交易笔数）→ 派生指标（加限定条件）→ 复合指标（不良率、净息差）；维度、同义词、业务描述同一"余额"在核心与信贷口径不同；一处定义、全局复用才不会"数出多门"metrics / cubes 定义 + 指标字典 + 责任人字段
③ 权限与治理层行级过滤（RLS）、列级脱敏（CLS）、指标×用户×维度授权、PII 标记、认证状态财富岗只看自己客户、投研岗不看明细；权限没下沉到语义层就过不了合规securityContext 规则 + 目录认证 + 审计日志
④ 服务暴露层把上述契约编译为受治理的查询接口：SQL / REST / GraphQL / MCP让问数 Agent 和自建 API 走同一个入口，避免治理体系外开新口子语义引擎 + 只读网关 + Golden queries

关键机制：大模型生成的是"语义查询"（WrenSQL / MQL），不是物理 SQL。引擎先按语义模型做校验、解析模型引用、注入计算字段，再转译成目标库方言后执行。WrenAI 的公开实现里，这一步是 dry-run 校验（DataFusion LogicalPlan + 类型检查），能拦下大量本来会打到数据库才暴露的错误。这正是"NL → DSL/MQL → SQL"两段式的工程含义。

13.2 银行特有的口径难题：必须在语义层显式处理

这些是通用语义层产品不会替你决定、但银行绕不开的部分。每一项都要在定义文件里写清楚，不能指望大模型临场发挥。

时点 vs 时期

余额类（存款余额、贷款余额）是时点量，取期末值，跨期求和是错的；发生额类（利息收入、交易金额）才是区间求和。指标必须带"时间属性"标签，否则 Agent 会把 12 个月的余额 SUM 成天文数字。

多币种折算

原币 / 折算币两套口径要分别定义；汇率来源（央行中间价 / 行内牌价）、折算日期（交易日 / 期末日）、是否重述都要固化。不能让每次问答现挑汇率。

机构层级与历史归属

网点撤并、分行改革后，历史数据归到新机构还是旧机构？机构树要有生效区间（SCD），否则同比环比会对不上，追溯时无法还原当时口径。

监管口径版本

EAST、1104、客户风险等监管字段与经营分析同源但口径不同。做法是公共指标全局唯一 + 监管专用指标保留版本，版本可追溯、口径调整后可回溯刷新历史报表。

多源日期对齐

核心、信贷、理财的数据日期常不对齐。邮储的"意图诊断模块"专门解决这个行业共性难题——语义层要记录每个数据源的可用日期与更新频率，问数时自动选齐口径。

客户与关联方口径

单一客户 / 集团客户 / 关联方三种合并口径必须有独立指标定义和权限边界，避免把集团风险敞口误答成单户敞口。

13.3 一个最小的定义示例

下面是 Wren MDL 风格的定义片段（用一个文件表达语义契约；Cube 的 cube 定义、dbt 的 semantic model 是同一思路）。重点是看清楚口径、关系、时间属性、权限分别写在哪里——而不是让大模型每次重新推导。

# models/deposit/metadata.yml — 逻辑模型：只暴露必要列
name: deposit_daily
table_reference: { schema: dw, table: dws_deposit_daily }
primary_key: acct_day_id
columns:
  - name: biz_date
    type: DATE
  - name: balance_cny
    type: DECIMAL(20,2)
    expression: "CASE WHEN ccy='CNY' THEN balance ELSE balance*fx_mid END"
    description: "按当日央行中间价折算的人民币余额"
  - name: org_id
    type: VARCHAR
  - name: customer
    relationship: deposit_to_customer   # JOIN 句柄，不在 SQL 里现写
properties:
  time_semantics: point_in_time          # 时点量：跨期取期末，不可累加
  data_owner: retail-deposit-team
  certified: true

# relationships.yml — 显式 JOIN，消除歧义
- name: deposit_to_customer
  models: [deposit_daily, customer]
  join_type: many_to_one
  condition: "deposit_daily.cust_id = customer.cust_id"

# cubes/deposit/metadata.yml — 指标：口径只定义一次
name: deposit_cube
base_object: deposit_daily
measures:
  - name: 存款余额
    expression: SUM(balance_cny)
    time_aggregation: end_of_period      # 明确期末口径
  - name: 日均存款余额
    expression: AVG(balance_cny)
time_dimensions:
  - name: biz_date
    expression: biz_date
dimensions:
  - name: 机构
    expression: org_id
synonyms: ["存款", "存款规模", "各项存款"]

示例为示意结构，字段以实际平台语法为准。真正重要的是四个设计点：未声明的列不可见、JOIN 显式声明、指标带时间属性、同义词映射到认证指标。

13.4 权限下沉：从语义模型继承，不在接口层手写

银行业最常见的失败是"问数很快，但权限是另一套"——Agent 走语义层，API 走自己的鉴权，久而久之出现越权后门。正确做法是把权限作为语义模型的一部分：

  • 行级：把"可见机构 / 可见客户 / 可见产品"做成随请求传入的 securityContext（通常来自 JWT 中的岗位与机构），由语义引擎在生成查询时动态拼接过滤谓词；用户无法绕过，因为物理表不直接暴露。
  • 列级：PII 字段在模型层标记为敏感，按角色决定返回原值、掩码还是拒绝；同一指标不同岗位看到不同明细粒度。
  • 指标级：支持"指标 × 用户 × 维度"细粒度授权——不是"能访问这张表"，而是"能看这个指标的这个维度组合"。
  • 可验证：用越权用例（不同角色、不同域、跨机构）作为发布门禁的一部分；全绿才允许接口注册。
注意产品差异：WrenAI 的 MDL 是 YAML + JSON manifest、可自托管、支持 20+ 数据源；许可证按路径区分，core/**、sdk/** 现为 Apache 2.0（AGPL-3.0 仅为未来模块预留，详见第 14 章更正）；Cube Core 为 Apache 2.0；dbt Semantic Layer 的 GraphQL/JDBC 接口依赖 dbt Cloud；Cortex Analyst / Databricks Genie / Fabric 的语义对象则绑定各自平台但治理链路更短。选型的核心不是功能多寡，而是定义文件能否掌握在 ETL 组自己的 Git 里、能否迁移、能否被审计重建。

13.5 六步落地：从零到可用的语义层

步骤做什么产出 / 卡点
1. 选域盘点挑一个数据域（如存款），列出 10–20 个高频指标，逐个找业务 owner 冻结口径卡：业务定义、计算公式、数据来源、维度、更新频率、时间属性、币种规则、责任人口径确认单；签字不齐不进入建模
2. 建逻辑模型把相关物理表映射成业务模型，显式声明主键、JOIN 基数与条件，只暴露必要列；给表和列写业务描述models / relationships 定义；validate 通过（无重复名、无缺失主键、无悬空关系）
3. 写指标定义原子 / 派生 / 复合分层，配置同义词与时间属性；把环比、同比等窗口逻辑沉淀为可复用计算字段，不让大模型每次现写metrics / cubes 定义 + 指标字典；每个指标必须有唯一 owner
4. 权限下沉配置 RLS / CLS / 指标级授权与 PII 标记；从身份系统透传岗位与机构上下文权限规则；越权用例集；越权零通过才放行
5. 编译发布PR 审阅 → validate → build 成 manifest → 目录认证 → 通过 SQL/REST/MCP 暴露为只读服务；高频指标配置预聚合加速版本化 manifest + 只读端点；评测不过阻断发布
6. 回归与追溯每次语义或口径变更自动跑 Golden set（30–100 条真实问题）回归；保存语义快照（当时的字段映射、度量公式、关联关系），口径调整后可还原历史并回溯刷新回归报告 + 语义快照；漂移拦截数纳入验收

13.6 让它"可追溯"的两个工程细节

口径规则抽成参数，不写死 SQL

ETL 脚本里不要把可变口径写死；抽成参数表并单独记录版本。追溯时看参数表历史版本即可，不用 diff 几百行脚本——这是银行监管报表追溯实践里反复强调的一点。

语义快照随每次发布留存

报表或定时查询触发时，自动保存当时的模型元数据（映射、公式、关联）快照。多数 BI 工具实时读最新模型，这会留下追溯盲区；语义快照补的就是这个缺口。

ETL 组的边界不变：语义层里可以自动做的是——从元数据生成模型草稿、从指标字典生成定义草稿、口径变更时跑回归、生成文档与同义词建议；不能自动生效的是——指标口径冻结、权限规则、发布认证。这三类必须走 owner 签字和 PR，与第 8 章的副驾驶模式完全一致。

14. Wren MDL 详解

先更正一条旧信息：早期资料（包括上一版报告）常说 WrenAI 是 AGPL-3.0。按官方仓库当前 LICENSE，这是多许可证布局：core/**、sdk/**、skills/**、examples/** 及根文件为 Apache 2.0，docs/** 为 CC BY 4.0；AGPL-3.0 文本只是为未来可能引入的模块预先放置，目前未映射到任何路径。对银行商用评估而言这是实质性利好，但落地前仍应让法务按"实际取用的包 + 其 package manifest 声明"复核——官方明确说manifest 与总 LICENSE 冲突时以 manifest 为准。

14.1 它是什么：语义契约，不是注释

MDL（Modeling Definition Language）是 Wren AI 的核心语义契约。官方定义很直接："Raw schemas describe storage. MDL describes meaning."（原始 schema 描述存储，MDL 描述含义。）它告诉 Agent、应用和人：有哪些数据集、暴露哪些字段、实体之间如何关联、哪些计算可复用、哪些查询形态应被当作稳定接口。

官方把上下文分成五层，MDL 承载前三层，这也是理解它边界的关键：

层内容状态（官方标注）由什么承载
Structural 结构层表、列、类型、键、物理关系已提供MDL 的 models / columns / relationships
Semantic 语义层业务命名的模型、可复用计算、权威表、枚举定义已提供MDL 的 calculated fields / views / cubes
Business 业务层公司特有定义（活跃客户、收入、流失）与内部命名已提供knowledge/glossary、metrics
Operational 运营层批准的 join 路径、许可查询、治理约束开发中knowledge/rules（部分）
Behavioral 行为层历史查询、成功 SQL、用户反馈、语义示例开发中knowledge/sql + memory
银行视角的重要提醒：官方明确标注 Operational 与 Behavioral 两层"in development"。对银行而言，权限策略、批准 join 路径、审计这类运营级治理不能依赖尚在开发的层——这正是前面反复强调"权限判定留在自己的语义层与网关"的原因。MDL 可以用，但不要把它当成完整治理系统。

Viewviews/<name>/metadata.ymlname + statement（完整 SELECT）；列声明不继承，查询时从语句推断；可递归引用其他 view
Cubecubes/<name>/metadata.ymlbase_object、measures[]（聚合值）、dimensions[]、time_dimensions[]、hierarchies（下钻）、refresh_time；通过 wren cube query 结构化查询，不写 GROUP BY
Knowledgeknowledge/**rules/ 业务规则（可带 exclude_rows、require_rate_join 等确定性约束）；sql/ verified NL-SQL 对；glossary/metrics/caveats

还有一个容易被忽略的机制：列重命名。当 is_calculated: false 但写了 expression 时，表达式必须是简单列引用——例如对外暴露名 customer_id、物理列 usr_id。这让"业务字段名"和"遗留系统字段名"解耦，对银行核心系统尤其有用。

一个已知限制：官方明确说明，关系句柄不能直接在查询里遍历——SELECT orders.customer.first_name FROM orders 会报 "No field named orders.customer.first_name"，因为关系列被排除在模型注册给引擎的 schema 之外。正确做法是用同一模型上的计算列穿透句柄（如计算列 customer_name 的表达式写 customer.first_name）。对 TO_MANY 关系，穿透的计算列必须用聚合函数，引擎会把 join 包进聚合子查询防止行数膨胀。

14.4 编译链路：YAML → 引擎可读的 manifest

wren context build 把所有分散 YAML 编译成单一 target/mdl.json，供 Rust 引擎 wren-core（基于 Apache DataFusion）消费。字段名从 snake_case 转 camelCase：table_reference→tableReference、ref_sql→refSql、is_calculated→isCalculated、join_type→joinType、base_object→baseObject 等；layoutVersion 由 build 自动写入，不要手填。

生命周期命令（官方 CLI）：

  • wren context init — 脚手架：空项目、v5 布局，或从既有 MDL JSON / OSI / dbt 转换
  • wren context validate — 按 schema_version 校验结构（重复名、缺失主键、悬空关系、列类型）
  • wren context build — 编译成 manifest；wren context show 检查；wren context upgrade --dry-run 可预演版本升级
  • wren memory index / fetch / store — 索引业务规则与 NL-SQL 对、按问题取相关上下文、把成功查询沉淀回 knowledge/sql/
  • wren dry-plan / wren dry-run / wren cube query — 计划转译、语法与库级权限校验、Cube 结构化查询

14.5 查询正确性：四道校验 + 声明式默认值

这是 MDL 对银行最有价值的部分——它不只"生成 SQL"，而是在执行前做多层校验：

1 · Schema Linking

wren memory fetch 只取与当前问题相关的模型、列、关系子集，避免 token 耗尽与提示词混淆。

2 · Dry-Plan

wren dry-plan 把建模 SQL 转译到目标方言、解析关系路径、应用策略过滤。

3 · Dry-Run

wren dry-run 对活库校验语法与库级权限，不返回完整结果集。

4 · Structured Errors

返回显式结构化错误对象，让 Agent 自我纠正，而不是把错 SQL 直接打到生产库。

此外，knowledge/rules/*.md 可声明确定性约束（如 exclude_rows 排除内部行、require_rate_join 要求汇率关联、sale_statuses 限定状态），引擎用 AST 检查（DefaultsChecker）在不实际执行的情况下验证查询是否遵守。这几乎就是我们前面说的"口径未确认不上线"的机器可读版本——可以直接把银行的时间属性、折算规则写成这类规则。

14.6 引擎与生态

wren-engine 已并入 Canner/WrenAI 的 core/ 目录，模块划分清晰：

  • wren-core：Rust 语义引擎，基于 Apache DataFusion 做 MDL 分析、计划与优化
  • wren-core-base / wren-core-py：共享 manifest 类型 / PyO3 Python 绑定
  • ibis-server：FastAPI 服务，负责查询执行、校验、元数据与连接器
  • mcp-server：MCP server，让任意 MCP 客户端（Claude Desktop、Cursor、VS Code 等）查询受治理数据

数据源（开源版官方列举）：Amazon S3、Spark、Apache Doris、Athena、BigQuery、ClickHouse、Databricks、DuckDB、GCS、本地文件、MinIO、MySQL、Oracle、PostgreSQL、Redshift、SQL Server、Snowflake、Trino 等。互操作：支持从 dbt manifest.json/catalog.json、OpenMetadata、Apache OSI（Open Semantic Interchange）导入导出——这意味着银行已有的 dbt 资产和目录可以迁移进来，不必推倒重来。
